1Before we start

Today the console saves nothing: rules, call-outs, strikes and incidents are lost every time it restarts. This guide adds a database. The first part of the work can start now. The questions that shape the tables are all answered below.

Can start now

  • Check all settings when the app starts, and stop with a clear message if one is missing (Section 5).
  • Set up the database and the npm run db:migrate command (Sections 4, 7 and 8).
  • Save the rules, so rule changes survive a restart (Section 3).

Questions

Also needed: IDs instead of names

The console links agents and teams by name, so two people with the same name, or a renamed team, would mix up their records. Before people are saved (Phase 1), the console switches to Genesys IDs, which never change. This is coding work we already know about (backlog item 4), not a question.

Setup checklist

  • Confirm the app's server: most likely the existing EC2 instance (Section 4).
  • Create the database and its two logins on van-reservation-prod, once, in pgAdmin (Section 4).
  • Note the PostgreSQL version (step 1 of the pgAdmin steps), so local development uses the same one (Section 11).
  • Write the deploy script that runs db:migrate before restarting the app (Section 8).

3What gets saved, and when

The console keeps working the way it does today: it checks the floor every second and updates the screen straight away. The database is its record and its memory across restarts. Every time something happens on the floor or someone acts in the console, a record is also saved.

How a record is saved

  1. The console acts first. The call-out, acknowledgement or rule change shows on screen at once, as today.
  2. A record joins a queue. Records wait in the order they happened.
  3. About once a second, the queue is written in one go. Either the whole batch is saved or none of it is; a failed write is tried again with the same records in the same order. If the database is down, the floor keeps running and records wait in the queue (Section 10).

Most events add a new row (a call-out, a rule version, an audit entry). Actions on something that already exists, such as acknowledging a call-out or closing an incident, update its row, so it always shows its latest state. Nothing is deleted.

How it fits together

Three rules for the design

RuleWhy
The engine never waits on the databaseA slow query or a failover would freeze every timer on the floor. Writes go into a queue and are flushed together, about once a second.
One engine processThe engine's state is in memory, so two copies behind a load balancer would disagree. The console runs as one long-lived task. With one writer, two strikes can never be numbered at the same time; a unique key on the incident's call-out stays as a safety net.
The database enforces the business rulesOne incident per strike from 3 on, call-outs pointing at real rules and people, and the version of a rule that fired, are all checked by keys and indexes, not by our code.

4Hosting on AWS

For now the console reuses what is already running: the app on an EC2 instance, and its data in a new database on the existing RDS instance van-reservation-prod. Same instance, so no added cost. The console can move to an instance of its own later by changing one connection string.

PieceChoiceNotes
AppAn EC2 instance, one Node processMost likely the current host; to be confirmed. Runs next start under a process manager (systemd or pm2) that restarts it if it stops. Not Lambda or Amplify server rendering: they stop the process between requests.
DatabaseA new database, rtm_console, on the RDS instance van-reservation-prodIts own database, not a schema inside the Van Reservation one, with its own roles (Section 6). Backups, maintenance window and PostgreSQL version are the instance's.
SecretsAWS Secrets ManagerOne secret per RTM database role, plus the Genesys and VAPID secrets. Read at start-up through the EC2 instance profile, or written to an environment file only root can read.
NetworkSecurity groupsThe RDS security group already admits the Van Reservation app. Add the RTM EC2 instance's security group on port 5432, and nothing else.
LogsThe process manager, or CloudWatch LogsA failed start-up check (Section 5) appears as one readable message.
⚠ Sharing a production instance: ground rules

Van Reservation is live on this instance. The console must never be able to read its data or slow it down.

  • Separate database, separate roles. rtm_migrator and rtm_app can connect to rtm_console only; CONNECT on it is revoked from PUBLIC, and the RTM roles are granted nothing on the Van Reservation database (see the note after the setup steps below).
  • Capped connections. Each RTM role gets a CONNECTION LIMIT (for example 15 for the app, 3 for the migrator), so the console can never use up the instance's connection slots.
  • No instance-wide changes. No parameter-group edits, no extensions that need shared_preload_libraries, no reboots for RTM's sake. Anything like that waits for a dedicated instance.
  • Only deployed environments connect. Developers work against the local Docker database (Section 11), never against this instance.
  • Batched writes. The write-behind queue (Section 10) keeps the console's load to one small transaction about once a second.

Creating the database and roles in pgAdmin (once)

This is done once, by someone with the master login for van-reservation-prod, in pgAdmin. It creates only RTM objects: two roles, one database and its grants. Nothing on the Van Reservation database changes. From then on, db:migrate creates and changes the tables.

ObjectTypeSettings
rtm_migratorLogin roleConnection limit 3. Owns rtm_console. Used only by db:migrate.
rtm_appLogin roleConnection limit 15. Reads and writes rows; cannot create or change tables.
rtm_consoleDatabaseOwner rtm_migrator. CONNECT for the two RTM roles only.
Before you start in pgAdmin
  • Run one step at a time. In the Query Tool, highlight the statements for a step and press F5: pgAdmin then runs only the highlighted text. Step 4 (CREATE DATABASE) must run on its own; PostgreSQL refuses it when it is sent together with other statements.
  • Passwords go through the role dialog, not the Query Tool (step 3), so they never land in the Query Tool's history.
  • Check the server name in the Query Tool's title bar before each step: it must be van-reservation-prod, and the database must be the one the step names.
  1. Open a Query Tool on the postgres database. In the Object Explorer, expand the van-reservation-prod server, then Databases, right-click postgres and choose Query Tool. Roles belong to the whole instance, so this database is the right place for steps 1 to 5, and it keeps you out of the Van Reservation database. First, record what the instance is running: 
    SELECT version();          -- the PostgreSQL version: the local Docker image must match it (Section 11)
SELECT current_user;       -- the master user you are logged in as
SELECT datname FROM pg_database WHERE NOT datistemplate;   -- existing databases; rtm_console must not be listed yet
  2. Create the two roles. They are created without passwords, so nobody can log in as them until step 3. The GRANT lets the master user create a database owned by rtm_migrator and set its default privileges in step 6. 
    CREATE ROLE rtm_migrator LOGIN CONNECTION LIMIT 3;
CREATE ROLE rtm_app      LOGIN CONNECTION LIMIT 15;
GRANT rtm_migrator TO CURRENT_USER;
  3. Set the passwords in the role dialog. Right-click Login/Group Roles and choose Refresh. For each RTM role: right-click it, Properties, Definition tab, enter a long generated password (from a password manager, at least 32 characters), and Save. Store each password in AWS Secrets Manager straight away, one secret per role, and never in a file, chat or ticket.
  4. Create the database, highlighting this statement on its own: 
    CREATE DATABASE rtm_console OWNER rtm_migrator;
  5. Close the database to everyone else. By default every role may connect to a new database; this limits rtm_console to the RTM roles and the master user. (rtm_migrator connects as the owner.) 
    REVOKE CONNECT, TEMPORARY ON DATABASE rtm_console FROM PUBLIC;
GRANT CONNECT ON DATABASE rtm_console TO rtm_app;
GRANT CONNECT ON DATABASE rtm_console TO CURRENT_USER;
  6. Set the grants inside rtm_console. Right-click Databases, Refresh, then right-click rtm_console and open a new Query Tool on it: these grants apply only to the database the Query Tool is connected to. The default privileges give rtm_app read and write access to every table and sequence that rtm_migrator creates later, so no migration has to grant them one by one. 
    REVOKE CREATE ON SCHEMA public FROM PUBLIC;    -- already the default on PostgreSQL 15 and later
GRANT USAGE, CREATE ON SCHEMA public TO rtm_migrator;
GRANT USAGE ON SCHEMA public TO rtm_app;

ALTER DEFAULT PRIVILEGES FOR ROLE rtm_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO rtm_app;
ALTER DEFAULT PRIVILEGES FOR ROLE rtm_migrator IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO rtm_app;
    If any of these fails with permission denied, stop and note the version from step 1: instances older than PostgreSQL 15 handle the public schema differently, and the statements need adjusting.
  7. Check the result. In the Query Tool on postgres: 
    SELECT rolname, rolcanlogin, rolconnlimit
FROM pg_roles WHERE rolname LIKE 'rtm\_%';     -- two rows: limits 3 and 15

SELECT datname, pg_get_userbyid(datdba) AS owner
FROM pg_database WHERE datname = 'rtm_console';  -- owner rtm_migrator
  8. Test the app login. In pgAdmin, Register → Server: the same host and port as van-reservation-prod, maintenance database rtm_console, user rtm_app, SSL mode require, and Save password left off. In a Query Tool on that connection: 
    SELECT current_user, current_database();    -- rtm_app, rtm_console
CREATE TABLE should_fail (x int);           -- must fail: permission denied for schema public
    Then remove the test server registration. A successful login from your PC only works if the RDS security group admits it; the deployed app connects from the EC2 instance.
The Van Reservation database

PostgreSQL lets every role connect to an existing database unless CONNECT was revoked from PUBLIC there, so rtm_app may be able to open the Van Reservation database. It still cannot read any of its tables unless they were granted to PUBLIC. To confirm, open a Query Tool on the Van Reservation database and run:

SELECT table_schema, table_name, privilege_type
FROM information_schema.role_table_grants
WHERE grantee = 'PUBLIC'
  AND table_schema NOT IN ('pg_catalog', 'information_schema');   -- expect no rows

Revoking CONNECT from PUBLIC on the Van Reservation database would close this fully, but it is a change to Van Reservation: do it only with its owner's agreement, after checking which roles its app uses.

Undoing it

Until the console has stored real data, the whole setup can be removed without touching anything else. On the postgres database, one statement at a time: DROP DATABASE rtm_console; then DROP ROLE rtm_app; then DROP ROLE rtm_migrator;

Moving out later

When the console needs its own instance (more load, its own maintenance window, an extension that needs a parameter change), dump rtm_console with pg_dump, restore it on the new instance, and change DATABASE_URL. Nothing in the code depends on sharing.

AWS credentials in the app

On EC2 the app uses the instance profile through the AWS SDK's default credential chain: no access keys in the environment. Explicit keys are accepted only for local work, and the environment check refuses half a set: a key without its secret, or a temporary ASIA… key without its session token.

5Configuration: one validated environment

Today eight files read process.env directly, and a missing value shows up only when a feature first needs it. After this change the application reads one parsed, typed object, and a broken deployment fails at start-up with a message that names every problem.

How it works

  1. lib/env.ts exports parseEnv(raw), a pure function that checks a set of variables against a Zod schema and returns a typed object. It is what the tests call.
  2. The same file exports env(), which parses process.env once and caches the result. Everything else in the app imports env(); nothing else reads process.env.
  3. instrumentation.ts calls env() in register(), on the Node.js runtime. If anything is wrong the server stops before it accepts a request, and the log lists every failing variable with its reason, not just the first.

The rules every variable follows

RuleIn practice
No silent default for a secretPasswords, tokens and keys are required where they are needed and never filled in for you.
Empty is not missingKEY= sets an empty string, which fails validation. A commented-out # KEY= means the variable is absent, which is allowed for optional settings.
Safe values may defaultFor example DB_PORT (5432), DB_POOL_MAX (10), RTM_TIME_ZONE (America/New_York).
Pairs are checked togetherBoth Genesys OAuth values or neither; all three VAPID values or none; PERSISTENCE_MODE=postgres requires database settings. These checks live in the schema, not in the code that uses them.
Stubs only where safePERSISTENCE_MODE=memory is accepted only when APP_ENV is development or test. It is an allowlist, so a new environment name is refused by default.
Why APP_ENV and not NODE_ENV

Every next build runs with NODE_ENV=production, including staging and a developer's production build. APP_ENV says which environment the server is really in.

6Connecting to PostgreSQL

One connection pool per process, created only when the first query needs it. The URL logic is a small pure module with its own tests, kept apart from Next.js.

How the URL is chosen

schemaFromUrl(url) reads the schema a URL points at from its search_path option. The tests use it to make sure they never run against the main schema.

Two roles, least privilege

RoleCanUsed by
rtm_migratorOwns the schema: create, alter and drop tables, indexes and partitions.db:migrate only, in the deploy script.
rtm_appSelect, insert, update and delete rows. Cannot change the schema. Granted through default privileges, so new tables are covered automatically.The running console.

If the app is ever compromised it cannot drop a table, and a typo in app code cannot alter the schema.

Encryption in transit

  • Whether the instance insists on TLS is set in its parameter group, which belongs to Van Reservation. The console uses TLS either way.
  • The app verifies the server against the RDS certificate bundle, kept on the EC2 instance with the app (DB_SSLMODE=verify-full).
  • On a PC behind corporate TLS inspection, DB_CA_CERT adds the company's certificate to the trusted list. Turning verification off is never the fix.
Why pg is kept out of the bundle

pg is added to serverExternalPackages in next.config.ts, next to exceljs and web-push, so Next.js loads it from node_modules at run time instead of bundling it.

7Migrations with Kysely

Kysely is a type-safe SQL query builder, not an ORM: queries read like SQL and are checked by TypeScript. Its migrator applies numbered TypeScript files in order and records each one in the database. kysely-ctl is its command-line tool.

The commands

CommandDoesNeeds the database
npm run db:migrateApplies every migration not yet applied, oldest first. Does nothing when up to date.Yes, as rtm_migrator
npm run db:make -- <name>Creates an empty, timestamped migration file to fill in.No
npm run db:statusLists the migrations and which are applied.Yes
npm run db:rollbackUndoes the last migration. Local only: refused when APP_ENV is staging or production.Yes
npm run db:typesRegenerates lib/db/schema.ts, the TypeScript description of every table, from a migrated database (kysely-codegen).Yes, local
npm run db:upStarts the local PostgreSQL container.No

Files

A migration, in outline

import { type Kysely, sql } from "kysely";

export async function up(db: Kysely<unknown>): Promise<void> {
  await db.schema.createTable("notification_route")
    .addColumn("route_id", "text", c => c.primaryKey())
    .addColumn("route_name", "text", c => c.notNull())
    .addColumn("enabled", "boolean", c => c.notNull().defaultTo(true))
    .execute();
  // ...then insert the four routes
}

export async function down(db: Kysely<unknown>): Promise<void> {
  await db.schema.dropTable("notification_route").execute();
}

The schema builder covers almost all of the design: identity columns, generated columns, check constraints, partial indexes and deferrable foreign keys. The rest, such as PARTITION BY RANGE, is written with Kysely's sql template inside the same migration.

Rules for writing migrations

RuleWhy
Never edit a migration that has run outside your machineIt will not run again anywhere it already ran. Write a new one.
Production goes forward onlydown() is for local work. A bad change in production is fixed by a new migration.
Reference data belongs in migrationsRoutes, default rules, status mapping and regions are written once, by the migration that creates their table. A later rule edit by an Admin is never overwritten.

Safe to run twice, safe to run together

Kysely records applied migrations in kysely_migration and holds a lock in kysely_migration_lock while it works. Running db:migrate again does nothing, and two runs at once wait for each other. It also refuses to apply an older file after a newer one has run, which catches a branch merged out of order.

8Running db:migrate before a deployment

The RDS instance has no public address, so db:migrate has to run from inside the VPC: from a laptop it cannot connect. The EC2 instance that runs the console is inside the VPC, so the deployment runs it there, after the new code is built and before the app is restarted.

Step by step

  1. On the EC2 instance, get the new code into a new release folder and run npm ci and npm run build there. The running version keeps serving the floor from its own folder; building over it would replace the .next folder it is using.
  2. Run npm run db:migrate with the rtm_migrator credentials, set for that one command only (for example read from Secrets Manager into DATABASE_URL). The app's own environment holds only rtm_app.
  3. Exit code 0: point the process manager at the new release folder and restart the console. On start-up it validates its settings and loads its rules from the new schema. The previous folder stays for a quick rollback of the code.
  4. Anything else: stop. Do not restart: the running console is untouched, because a failed migration is rolled back inside its transaction. Read the error, fix it with a new commit, and deploy again.

These steps go into a deploy script in the repository (for example scripts/deploy.sh), so a deployment is one command and the migration can never be skipped.

The migrator touches only rtm_console

rtm_migrator owns rtm_console and has no rights on the Van Reservation database, so a migration cannot change anything but the console's own tables, however it is written.

Write migrations the old code can live with

For a short time the old app runs against the new schema. Add columns and tables freely. To rename or remove one, use two releases: first stop using it, then drop it.

Running it by hand

To run a migration from a laptop, for example to check a new one against a copy of the data, open an SSM port-forwarding session to the database through the EC2 instance, point DATABASE_URL at the forwarded local port with the migrator's credentials, and run npm run db:migrate. Keep this for emergencies; the deploy script is the normal route.

The 20 tables in the PostgreSQL Schema doc are kept. These are the corrections found in review, each to match how the engine actually runs. Each one is made in the first migration of its table.

At start-up the counter continues from incident_counter; the flush writes the counter, incident and call-out in one transaction. With one engine process there is no race.

10How the engine saves and recovers

The engine keeps working exactly as it does today. What changes is that every record it makes is also handed to a store, and that on start-up it begins from what the store remembers instead of from nothing.

The store

Memory store

Keeps nothing beyond the process. Used in development without a database, in unit tests, and always for CSV replays. Refused in staging and production.

PostgreSQL store

Queues each record in order and flushes the queue in one transaction about once a second. A failed flush is retried with the same records in the same order; the console raises a notice if the queue keeps growing.

On start-up

  1. Validate the environment (Section 5). Stop if anything is wrong.
  2. Load the rules at their current version. In Phase 0 this is the only step.
  3. From Phase 2: find or open the shift for today's Eastern date, then load today's strike counts, every open call-out and incident from any day, and the incident counter.
  4. From Phase 3: rebuild today's KPIs from the events in source_event_stream.
  5. Connect the feed. Genesys gives each agent's time already in state; rules an agent is past are marked fired without a call-out, as today.

What is never stored

DataWhy not
Live timers (time in state, hold time)Taken again from Genesys at connect.
The fired flag per rule episodeRebuilt at connect (Section 9).
CSV replaysPrivate to the session that started them.
The Genesys tokenA secret: it stays in the environment or Secrets Manager, never in a table.
If the database is down

The floor keeps running: timers, call-outs and alerts carry on from memory, and records wait in the queue. A start-up with the database unreachable fails, because the engine cannot know the current rules or strikes.

11Local development and tests

A developer can work with no database at all, as today, or against a local PostgreSQL in Docker that behaves like RDS. Developers never connect to van-reservation-prod.

First run with a local database

  1. Copy .env.example to .env.local and set APP_ENV=development, PERSISTENCE_MODE=postgres and the DB_* values given for the container.
  2. npm run db:up starts PostgreSQL in Docker on port 5435, so it never clashes with a PostgreSQL already installed on 5432 or with other local containers on 5433 and 5434.
  3. npm run db:migrate creates every table and the reference data.
  4. npm run dev as usual. Rule edits now survive a restart.

To work without a database, set PERSISTENCE_MODE=memory. Nothing else changes.

12Delivery plan and acceptance checks

Four phases, ordered by what each is waiting for. Each phase is its own pull request, and its migration is final once merged.

Phase 0 · Foundation Can start

Typed environment and boot check, database URL module, Kysely and db:migrate, local PostgreSQL, reference-data migration, the store, and rules that survive a restart.

Phase 1 · People and queues Needs real IDs

The engine carries Genesys user IDs. person, team, queue and queue_member are synced from the roster; push subscriptions move into the database.

Phase 2 · Shift records After Phase 1

Shifts, call-outs, incidents, strikes and delivery records, with the write-behind queue and recovery after a restart.

Phase 3 · Raw events After Phase 2

Today's Genesys events with batched inserts, emptied at midnight Eastern. The day's KPIs survive a restart.

Phase 0 is done when

  • .env.example copied as it is fails the start-up check, safely and readably.
  • One run of the check reports every failing variable, not only the first.
  • Commented-out optional variables work; empty strings are refused; the pair rules are tested.
  • DATABASE_URL precedence, DB_* composition and schemaFromUrl() are tested.
  • The memory store is refused outside development and test; partial or temporary AWS keys without a session token are refused.
  • The Docker database matches .env.example, and db:make works with no database settings.
  • db:migrate on an empty database creates the Phase 0 tables and reference data; a second run does nothing.
  • An edited threshold is still there after a restart, with its old value kept as an earlier version.
  • npm run typecheck, npm run lint and npm test pass.

13Frequently asked questions

Why Kysely and not an ORM such as Prisma?
The schema leans on PostgreSQL features (partial unique indexes, partitions, deferrable keys, generated columns) that ORMs hide or do not support. Kysely writes plain SQL with TypeScript checking, and its migrations are ordinary TypeScript files in the repository.
Do I need a database to work on the console?
No. PERSISTENCE_MODE=memory runs it exactly as it runs today.
Can I run db:migrate from my laptop against AWS?
Not directly: the database has no public address. Use the deploy script on the EC2 instance, or in an emergency an SSM port-forward (Section 8).
What happens if a migration fails halfway?
It runs in a transaction, so PostgreSQL rolls it back and the database is as it was. The deploy script stops before restarting the app, and the running console is untouched.
Can sharing van-reservation-prod affect Van Reservation?
Only through load, and that is capped: connection limits on the RTM roles, batched writes, and no changes to the instance itself. The RTM roles cannot read or change Van Reservation's data. If the console's load ever matters, it moves to its own instance (Section 4).
Should developers point at the shared instance?
No. It is a production instance. Develop against the local Docker database; only the deployed console connects to rtm_console.
Can we run two copies of the console for resilience?
Not yet. Two engines would disagree. A second web tier needs the engine to publish each tick through a broker such as Redis (data architecture document, Section 9).
Will an Admin's rule edits be overwritten by a later migration?
No. Default rules are inserted once, by the migration that creates the table. Changing a default for new installs means a new migration that touches only rules nobody has edited.
Where do the real passwords go?
In AWS Secrets Manager for deployed environments and in .env.local on a developer's PC. Neither is ever committed: the repository is public.
